Kouchou AI / keyword-curation workflow

日本語版

Overview

This directory contains a working workflow for organizing the entities and relationships that appear in the first 3,000 records of raw public-comment data on Japan’s Seventh Strategic Energy Plan (February 2025), obtained through a freedom-of-information request. The workflow starts from intermediate outputs produced by running those CSV comment records through the Kouchou AI report-generation pipeline, and then uses entity-linking results manually checked with keyword-curation.

In previous work, I, Akihiro Kameda at the National Institutes for the Humanities, have collaborated with Kohei Ishii of Chiba University on analyses of environmental policy formation processes using BERTopic and related methods, including topic-composition comparisons based on minutes from environmental policy councils. Those analyses have covered minutes, public comments, policy documents, and other environmental-policy materials.

In expanding that line of work to the policy-formation process around energy policy, several recent public discussions were especially relevant:

  • More than 41,000 public comments on the Strategic Energy Plan, a record high; concerns about nuclear power reflected in the plan: Asahi Shimbun
  • Possible AI use in public comments on the Strategic Energy Plan, nearly 4,000 submissions: Nikkei

Against that background, I referred to the publicly available materials, but the analysis in this workflow uses only raw data obtained separately through a freedom-of-information request. Specifically, it processes the first 3,000 records from that raw data. The goal was to extract meaningful entities and relationships from a large set of highly similar comments. I also aimed to make the workflow compatible with practitioner workflows by building it around existing tools such as Kouchou AI.

The input is a set of intermediate files generated by processing a comment CSV through the Kouchou AI report-generation pipeline: hierarchical clusters, arguments, embeddings, and related files. From these, the workflow uses L2 cluster labels and takeaways to generate entity-linking candidates, then uses manually checked results for downstream relationship extraction. In the JSON file used by keyword-curation, this auxiliary context is passed as each item’s description.

The output is a discussion viewer that lets users browse a network of entities and entity-level or pair-level opinion summaries based on the comments. The workflow seems to have some value in that it can surface a small number of important opinions that would otherwise be difficult to identify.

Future work includes academic validation, evaluation, and improvements that would make this workflow easier for practitioners and other researchers to use in real settings.

Workflow

0. Process the CSV with Kouchou AI

First, feed the original comment CSV into the Kouchou AI report-generation pipeline. This step extracts arguments from comment bodies, creates argument embeddings, and performs hierarchical clustering and cluster-label generation for the arguments.

The required CSV columns vary slightly depending on how the data is passed into Kouchou AI. When running the pipeline directly with a CSV file, the minimum columns needed for processing are comment-id, which identifies the unit of processing, and comment-body, the comment text passed to the LLM. When uploading a CSV through the Web UI, if neither id nor comment-id is present, the UI automatically assigns IDs.

On the other hand, source and url are standard columns in input plugins and in the internal Web UI/API data model. For reproducibility and source links, it is safer to include them as well. The input CSV used in this experiment had the following columns:

  • comment-id: an ID for each comment. It is used in Kouchou AI’s relations.csv to link extracted arguments to comments, and it remains as comment-id in final_result_with_comments.csv.
  • comment-body: the original comment text. It is used for Kouchou AI’s argument extraction and is output as original-comment in final_result_with_comments.csv. This workflow generates dataset/energy-plan-pubcom-sample/comment_texts.json from it.
  • source: the origin of the comment. It is not required for direct pipeline execution, but input plugins output it as a standard field. If present, it remains in Kouchou AI’s final_result_with_comments.csv.
  • url: a URL for the original comment or source. It is not required for direct pipeline execution, but is needed when using source-link features. If present, it remains in Kouchou AI’s final_result_with_comments.csv, and depending on the configuration it may also appear as url on the argument side of hierarchical_result.json.
  • attribute_...: additional attribute columns attached to comments. Columns whose names begin with attribute_ are treated as attributes in Kouchou AI’s aggregation step. They remain under their original names in final_result_with_comments.csv; in hierarchical_result.json, they appear in arguments[].attributes with the attribute_ prefix removed.

In short, comment-id and comment-body are the minimum needed for processing. In Web UI/API/plugin use, source and url are effectively standard fields and are worth including. Other columns are preserved as metadata separate from the comment text in downstream intermediate files. The scripts in this workflow directly use mainly the arguments, cluster information, comment IDs, and original comment text; source and attribute_... remain as auxiliary information inherited from Kouchou AI.

The scripts in this repository do not run Kouchou AI itself. They read the dataset directory specified by DEFAULT_DATA_DIR in settings.py. To temporarily use another dataset, pass --data-dir dataset/<dataset-name> to each script. When Kouchou AI is run from the Kouchou AI repository root, intermediate files are usually written under apps/api/broadlistening/pipeline/outputs/, in a directory for each run ID.

After identifying the target run ID directory, copy the necessary intermediate files into this repository’s dataset/energy-plan-pubcom-sample/ directory.

cp /path/to/kouchou-ai/apps/api/broadlistening/pipeline/outputs/<run-id>/hierarchical_result.json dataset/energy-plan-pubcom-sample/
cp /path/to/kouchou-ai/apps/api/broadlistening/pipeline/outputs/<run-id>/hierarchical_clusters.csv dataset/energy-plan-pubcom-sample/
cp /path/to/kouchou-ai/apps/api/broadlistening/pipeline/outputs/<run-id>/final_result_with_comments.csv dataset/energy-plan-pubcom-sample/
cp /path/to/kouchou-ai/apps/api/broadlistening/pipeline/outputs/<run-id>/embeddings.pkl dataset/energy-plan-pubcom-sample/
  • dataset/energy-plan-pubcom-sample/hierarchical_result.json is used to extract L2 cluster labels and takeaways for entity-linking candidate generation.
  • dataset/energy-plan-pubcom-sample/hierarchical_clusters.csv is used to look up which L1/L2 clusters each argument belongs to.
  • dataset/energy-plan-pubcom-sample/final_result_with_comments.csv is used to connect arguments with original comment text and comment IDs.
  • dataset/energy-plan-pubcom-sample/embeddings.pkl is used to divide arguments into finer local clusters.

Here, an L2 cluster label means the representative label assigned to a second-level cluster after Kouchou AI hierarchically clusters arguments extracted from comments. It is treated as a short description of an issue category that groups multiple arguments, not as the text of an individual comment. A takeaway is auxiliary context: a textual summary of the main point of the same cluster. Because takeaways may contain specific technologies, institutions, or policy terms that do not appear in the short L2 label, this workflow uses them both for entity-linking candidate extraction and for manual review.

In addition to the four files copied from Kouchou AI, this repository also generates dataset/energy-plan-pubcom-sample/comment_texts.json from dataset/energy-plan-pubcom-sample/final_result_with_comments.csv. Raw summaries and some quoted source comments are included in the data.

1. Generate entity-linking candidates

scripts/prepare_entity_candidates_no_draft.py reads the L2 cluster labels and takeaways from dataset/energy-plan-pubcom-sample/hierarchical_result.json. It uses an LLM to extract terms that are likely to be linkable to Wikidata, searches the Wikidata Search API for candidates, and selects the most appropriate QID.

The output is dataset/energy-plan-pubcom-sample/data.json. Each item contains the L2 cluster label and the Kouchou AI takeaway as its description. At this stage the result is automatically generated, so the entity_id, label, description, and link/no-link decisions should be manually checked in keyword-curation while referring to the description.

python scripts/prepare_entity_candidates_no_draft.py

2. Refine entity descriptions

scripts/refine_entity_descriptions.py rewrites the entity descriptions in the curated dataset/energy-plan-pubcom-sample/data.json into short Japanese descriptions.

This helps stabilize the meaning of each entity for downstream graph visualization and LLM-based opinion extraction.

python scripts/refine_entity_descriptions.py --only-weak

3. Create local clusters of arguments

scripts/build_argument_microclusters.py applies Ward clustering to argument embeddings and groups semantically close arguments into local clusters. These local clusters are separate from the overall hierarchical clusters; they further subdivide arguments that are semantically close. Because Kouchou AI extracts arguments comment by comment, many semantically redundant arguments can be produced when comments are similar. This was a particular issue in the public-comment data used here, so this process was added.

The inputs are dataset/energy-plan-pubcom-sample/embeddings.pkl and dataset/energy-plan-pubcom-sample/hierarchical_clusters.csv. The output is dataset/energy-plan-pubcom-sample/argument_microclusters_t0.7.csv. Each local cluster includes a centroid argument, which makes it easier to select representative issues in later steps.

python scripts/build_argument_microclusters.py --threshold 0.7

4. Build an index of comments and clusters

scripts/build_cluster_comment_index.py creates an index that connects arguments, comment IDs, hierarchical clusters, and local clusters.

The inputs are dataset/energy-plan-pubcom-sample/final_result_with_comments.csv, dataset/energy-plan-pubcom-sample/hierarchical_clusters.csv, and dataset/energy-plan-pubcom-sample/argument_microclusters_t0.7.csv. The outputs are:

  • dataset/energy-plan-pubcom-sample/cluster_comment_index.csv: an index for publication and analysis
  • dataset/energy-plan-pubcom-sample/comment_texts.json: a local reference file mapping comment IDs to comment text
python scripts/build_cluster_comment_index.py

5. Discover Wikidata property paths

scripts/discover_property_paths.py examines QID pairs that co-occur within the same L2 label. It checks Wikidata properties such as P31, P279, P361, and P527, and searches for direct relationships or shared upper classes.

The outputs are:

  • dataset/energy-plan-pubcom-sample/property_paths.tsv: discovered relationships
  • dataset/energy-plan-pubcom-sample/entity_props_cache.json: a cache of Wikidata API results
python scripts/discover_property_paths.py

6. Build the entity graph

scripts/build_entity_graph.py builds an entity-centered graph from dataset/energy-plan-pubcom-sample/data.json and dataset/energy-plan-pubcom-sample/property_paths.tsv. Nodes are controlled entities, one per entity_id, after manual checking in keyword-curation. If the same entity appears in multiple L2 clusters, the node aggregates the relevant item_ids and surface forms.

The graph has two types of edges:

  • co_mention: co-occurrence within the same L2 label. These edges connect entities that appear in the same issue category in the comments.
  • wikidata_property: relationships based on Wikidata properties. These are based on direct relationships or shared upper classes found through properties such as P31, P279, P361, and P527.

At this stage, edges are not relationships explained by reading the comment text. They are structural clues based on co-occurrence and Wikidata. In the subsequent pair-relation extraction step, the weight of co_mention edges is used to select pairs for explanation.

The output is dataset/energy-plan-pubcom-sample/entity_graph.json.

python scripts/build_entity_graph.py

7. Extract opinions for each entity

scripts/extract_entity_opinions.py gathers comments corresponding to clusters in which each entity appears, then uses an LLM to extract the stance toward that entity, major opinion points, and candidate relationships with other entities. The LLM input includes the focal entity, comments from L2 clusters in which the entity appears, and the list of curated entities.

The output field relations indicates candidates for “which other entities this entity is discussed in relation to” based on the comment text. Relation types include promotes, opposes, requires, replaces, risk_of, compared_with, causes, and solution_for. This list is fixed in the prompt in scripts/extract_entity_opinions.py; it is not generated automatically from the data. The current list is a working classification designed for energy-policy comments, and it may need to be replaced when the target data or analytical purpose changes. These relation types are not final labels displayed directly in the viewer; they are LLM-derived clues for selecting pairs to explain in the next step.

The input requires dataset/energy-plan-pubcom-sample/comment_texts.json. The output is dataset/energy-plan-pubcom-sample/entity_opinions.json.

python scripts/extract_entity_opinions.py --resume

8. Extract pair-level relationships

scripts/extract_pair_relations.py uses dataset/energy-plan-pubcom-sample/entity_opinions.json and dataset/energy-plan-pubcom-sample/entity_graph.json to select high-scoring entity pairs, then asks an LLM to generate pair-level relationship descriptions.

Pair selection combines the number of relations extracted in step 7, whether there are bidirectional relationship clues, and the weight of co_mention edges created in step 6. Pairs above the threshold are used as the base set; if the graph would otherwise become disconnected, lower-scoring auxiliary pairs are added to preserve connectivity.

For explanation generation itself, the prompt does not directly pass the relation types from relations. Instead, it passes the two selected entities and the comments from L2 clusters where both appear, or the union of their related comments if there is no shared cluster. Therefore, the descriptions in dataset/energy-plan-pubcom-sample/pair_relations.json are newly generated from the comment text, rather than being a direct restatement of the clues used for pair selection.

The output is dataset/energy-plan-pubcom-sample/pair_relations.json.

python scripts/extract_pair_relations.py --resume

9. Generate the discussion viewer

scripts/build_pair_relation_viewer.py generates a static HTML page that reads dataset/energy-plan-pubcom-sample/pair_relations.json and dataset/energy-plan-pubcom-sample/entity_opinions.json in the browser.

The output is dataset/energy-plan-pubcom-sample/pair_relation_viewer.html.

python scripts/build_pair_relation_viewer.py

Steps that call an LLM require OPENAI_API_KEY.
